# 2026-08-10 工作日志

- 为用户准备明日面试材料：基于 IndustrialDAQ 项目，整理岗位匹配分析、项目讲解要点、42 道上位机软件开发工程师模拟面试题及重点答题思路，输出到 `面试准备-IndustrialDAQ.md`。
- 排查 Modbus TCP 写入不同步问题（初版误判）：初版假设 S7 MB_SERVER 有 MB_COILS_START 参数，把 C# Coil 地址改成 00001-00012，用户实测仍无效。
- 二次确诊根因（正确）：西门子标准 MB_SERVER 的 `MB_HOLD_REG` 只映射保持寄存器（HR/IR）到指定 DB（DB4）；**线圈/DI 走 MB_SERVER 实例 DB（DB3）内部缓冲**，不经过 DB4。用户 PLC 程序读的是 DB4.coils[0]/coils[1]（byte 24/25），而 C# 用 FC5 写线圈进的是 DB3，故"返回成功但 PLC 不变"。DB4 实测结构已确认 coils 在 byte 24-25。
- 给出三套修复方案：A) 用 HR 寄存器 40013 读写 coils 字节（大端打包，注意读-改-写）；B) PLC 拷贝 DB3 线圈缓冲到 DB4（偏移随固件变，不推荐）；C) DB4 新增 HR_Control/HR_Status 专用字，命令/状态分离，彻底不用线圈（推荐）。已重写诊断报告 `config/诊断报告-Modbus写入不同步.md`。
- 落地方案 C 的实现：发现原驱动不支持「Bool + HR 地址」（WriteTagAsync 走 PackRegisterValues 无 Bool 分支会抛 NotSupportedException，ReadTagsAsync 对 Bool+HR 只判断整寄存器 !=0 不按位提取）。因此在代码中新增按位访问支持：(1) `TagPoint` 增加 `BitIndex` 字段（默认 -1）；(2) `DeviceConfigurationLoader.TagPointDto` 透传 `bitIndex`；(3) `ModbusTcpDriver` 在读 HR/IR 时对 Bool+BitIndex>=0 提取该位，在写 HR 时对 Bool+BitIndex>=0 执行「读-改-写」保留同寄存器其他位。(4) `config/production-line.json` 的 8 个数字量标签改为 HR 控制字 40014（bit 0-3=Start/Stop/Auto/EStop）+ 状态字 40015（bit 0-3=Running/Alarm/Valve/Conveyor）。Core 与 Modbus 驱动均已编译通过，JSON 校验通过。PLC 侧仍待用户新增 HR_Control/HR_Status 并改映射。
- 审查"写入假成功"问题并修复 ModbusTcpDriver：审查结论——驱动与两个 ViewModel 的异常路径本身正确，假成功来自协议层无法感知的失败与环境回退：(1) ConnectAsync 仅 TCP 验证；(2) 写入只看"没抛异常"，从机 ACK 即成功；(3) SlaveException 信息不直观；(4) App.xaml.cs 配置失败时静默回退 Mock 设备（Mock 写入永不失败）；(5) OPC UA 设备与 Modbus 设备标签重名易写错设备；(6) 旧 DLL 未重建。修复（已编译 0 错 0 警告）：ConnectAsync 增加 Modbus 握手探测（读寄存器 0，SlaveException 视为在线）；WriteTagAsync 增加写后回读校验（线圈/按位/整寄存器三种路径，不一致抛"写入回读校验失败"）；SlaveException 包装为"Modbus 从机拒绝写入请求 (异常码 N)"。注意 NSModbus4 异常类型是 `Modbus.SlaveException`（非 Modbus.Device），且其 API 无 CancellationToken 重载。诊断报告新增"七、写入假成功问题审查与修复"。
- 放宽握手探测为非致命（用户截图反馈 13 个标签全部 Bad）：之前的握手探测在连接后立即读寄存器 0，对网络抖动或 PLC 启动延迟过于严格——一旦探测超时，ConnectAsync 失败 → DeviceCollector 永远连不上 → 所有读循环跳过 → 所有标签 Quality=Bad（连本应正常的 HR 浮点 40001/40003 也 Bad）。对 S7 MB_SERVER 而言端口 502 由 MB_SERVER 打开，TCP 连通已证明 MB_SERVER 在监听，握手多此一举且误伤。已将握手 `catch` 改为静默忽略，探测失败不影响 `_connected=true`；真正的"假成功"仍由 WriteTagAsync 的写后回读校验覆盖。重新编译 0 错 0 警告。诊断报告 7.3 第 1 条已同步注明"非致命"。
- 全标签 Bad 真正根因（握手放宽后仍 Bad）：**合并读取"一损俱损"**。`MergeAdjacentAddresses` 把 40001~40015 合并成一次读寄存器 0~14 共 15 个；但 DB4 只有字节 0~25（寄存器 0~12），40014/40015 对应字节 26~29 在 DB4 不存在 → MB_SERVER 回异常码 0x02 → 整组 13 个标签全 Bad（含正常 HR）。修复：`ReadTagsAsync` 批量读被协议层拒绝（SlaveException）时降级为逐标签单点读取（新增 `ReadSingleTagAsync`），隔离坏点；仅传输层异常（IO/超时）才整组失败。编译 0 错 0 警告。教训：Modbus 批量读一个地址越界拖垮整组，需保证合并范围地址真实存在或实现单点降级。诊断报告新增 7.5 节。
- 上位机地址 vs PLC 字节偏移修正：用户在 TIA 里把 `HR_Control` 直接放在原 `coils[0]/coils[1]` 占用的字节 24-25（UInt 覆盖两字节），`HR_Status` 在字节 26-27（替换原 coils 数组的位置，更合理）。但我之前的预期是字节 26/28 / 寄存器 40014/40015，与实际**偏移 2 字节**。已把 `production-line.json` 的 8 个数字量标签改为：命令 → 40013（HR_Control，byte 24），状态 → 40014（HR_Status，byte 26），合并读范围 0-13（byte 0-27）全部在 DB 内。`coils` 数组已从 DB 删除 → PLC 程序必然已删 `coils` 引用改用 `HR_Control/HR_Status`（TIA 否则编译不过）。诊断报告第 5 节地址描述待同步。
